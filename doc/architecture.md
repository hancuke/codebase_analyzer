# CodeGraph 架构设计

> 本文是文档先行的架构讨论稿。它规定责任、依赖方向和演进原则；不规定目录结构、数据结构或算法的最终实现。

## 架构目标

CodeGraph 需要同时做到三件事：

1. **调用简单**：调用者从 `Codebase` 开始，只提供文件和前端，再查询函数、调用、入口、上下文和刷新影响。
2. **结果可信**：图中每条边都有可靠解析或可审计的跨语言证据；不确定信息可见但不污染图。
3. **演进可控**：新增语言、链接协议、索引实现或刷新策略时，不改变调用者的主流程和结果契约。

它不负责编辑源码、编译项目、执行程序、调用 LLM、生成 prompt、存储向量或展示图。

## 总体分层

```text
                    上层应用
         CLI / CI / RAG / LLM / 文档工具
                         |
                         v
                 Public Facade
          Codebase / 请求 / 结果模型
                         |
                         v
             Application Orchestration
   分派 -> 聚合 -> 校验 -> 链接 -> 建快照 -> 刷新
              /                     \
             v                       v
      Extension Contracts        Core Domain
  LanguageFrontend / Linker   函数、调用、入口、诊断
             |                       |
             v                       v
        VBA / Java / ...       Graph Index / Traversal
```

依赖只能从上往下：公共外观依赖编排和领域模型；编排依赖领域模型和扩展协议；具体前端、链接器及图索引实现依赖协议或领域模型。核心领域模型不依赖任何语言、框架、LSP、文件系统或上层应用。

## 四个架构区域

| 区域 | 职责 | 可以依赖 | 明确不负责 |
| --- | --- | --- | --- |
| 公共外观 | 提供简洁 API，规范输入、返回快照和结果模型 | 编排、公共领域模型 | 暴露索引、解析树、插件内部类型。 |
| 应用编排 | 执行分析/刷新用例，控制顺序、汇总诊断和构造快照 | 核心领域、扩展协议 | 理解 VBA、Java 或路由语义。 |
| 核心领域 | 表达不可变事实，校验通用不变量，查询图、管理入口和影响范围 | 自身抽象 | 解析源码、猜测目标、读取文件。 |
| 扩展适配 | 处理具体语言与协议，产出统一分析事实及证据 | 扩展协议、领域模型 | 修改核心索引、定义公共 API。 |

这种分工的重点不是增加层数，而是使“变化原因”分离：语言变化只影响前端，业务入口变化只影响调用者策略，图优化只影响核心内部，公共 API 演进只影响外观和兼容层。

## 从输入到可查询快照的数据流

### 初次分析

```text
SourceFile[]
   |
   v
文件规范化与唯一性检查
   |
   v
FrontendRouter -- 每文件恰好一个 Frontend --> 分语言批次
   |                                              |
   |                                              v
   |                                        FileAnalysis[]
   |                                              |
   +--------------> 聚合和全局不变量校验 <---------+
                          |
                          v
                 CrossLanguageLinker[]
                          |
                          v
       函数表 + 已确定调用 + 未确定调用 + 诊断 + 候选入口
                          |
                          v
              SnapshotBuilder / GraphIndex
                          |
                          v
           AnalysisResult(codebase, diagnostics)
```

1. **规范化输入**只做路径和语言提示等通用校验，不读取或理解源码。
2. **路由**先确定每个文件的唯一前端，再按前端所需的语言范围批处理，避免跨文件语义受文件顺序影响。
3. **前端分析**产出函数、调用、候选入口和诊断。调用尚未确定目标也必须作为事实保留。
4. **聚合**校验函数 ID 全局唯一、调用源函数存在、位置合理等语言无关不变量。
5. **跨语言链接**只在全部本地结果稳定后执行。链接器只能依据显式证据补充目标和证据，不能依名称猜测。
6. **快照构造**只将已确定的内部调用写入直接边索引；未确定调用和诊断随快照保存，供调用者解释结果。

这里的关键边界是：前端与链接器提供**事实和证据**，核心提供**验证、索引和查询**。任何一方都不应直接改写另一方的内部状态。

### 刷新

刷新不是把局部变更直接塞进旧索引。架构上，它是一次新快照构造加一次旧新快照比较：

```text
旧快照 + 文件替换/删除
          |
          v
       新文件快照
          |
          v
       完整分析流程
          |
          v
  旧新函数/边差异 + 两张反向图
          |
          v
      受影响确认入口
          |
          v
 RefreshResult(新快照, 差异, 诊断, 入口)
```

首版使用全量分析可避免跨文件类型信息或跨语言契约过期。未来替换为增量策略时，必须生成与全量流程等价的函数、边、诊断和影响结果。

## 核心模型与不变量

核心模型应是无行为或小行为的不可变值对象，任何组件都只能创建新值，不可就地篡改已发布快照。

| 模型 | 核心不变量 |
| --- | --- |
| `SourceFile` | 在一个输入快照中路径唯一，内容完整，语言提示只影响路由。 |
| `Function` | ID 在代码库内唯一；来源文件与范围可追溯；ID 不由行号构成。 |
| `Call` | 总有来源、原始文本和位置；只有有可靠目标时才是内部图边。 |
| `ResolutionEvidence` | 记录目标由哪个前端/链接器、哪类契约和哪些位置确定。 |
| `Diagnostic` | 有稳定代码和严重级别；可附带位置和关联位置；不是仅字符串日志。 |
| `EntryPoint` | 指向已存在函数，携带业务类别与来源；不改变函数本身。 |
| `CodebaseSnapshot` | 函数、直接边、调用记录、候选入口、确认入口和诊断来自同一分析版本。 |

不可变快照使调用者可以安全保留一个分析结果、用它生成文档或比较刷新前后差异；也使实现者可以在以后加入缓存和并发，而不向公共 API 泄漏可变状态。

## 调用者 API 的外观原则

`Codebase` 是唯一的常规入口，承担发现能力的职责，但不承担所有实现细节。

```python
analysis = Codebase.analyze(files=files, frontends=frontends, linkers=linkers)
codebase = analysis.codebase

function = codebase.function(function_id)
calls = codebase.callees(function_id, transitive=False)
context = codebase.context_for(entry_id, limits=limits)
refresh = codebase.refresh(changed_files=changed, removed_paths=removed)
```

外观应满足以下规则：

* **按任务命名**：`context_for()` 表达调用者任务，不强迫其组合多个内部遍历 API。
* **读写分明**：查询不改变快照；入口更新和刷新产生明确的新状态或新快照，最终必须选定一种统一风格。
* **结果优先**：分析和刷新将诊断同结果返回；不能依赖控制台日志或宽泛异常传达可预期问题。
* **高级而不泄漏**：需要自定义解析时扩展 `LanguageFrontend`/`CrossLanguageLinker`，不需要创建 Repository、Resolver 或 Graph Builder。
* **稳定而不僵化**：参数避免暴露底层图结构；新增过滤和预算时优先以选项对象承载，以免方法签名不断膨胀。

## 扩展架构

### 语言前端

一个 `LanguageFrontend` 是语言适配器，不是核心插件容器。它的职责是：

1. 判断其是否支持一个文件；
2. 以该语言需要的批次读取完整文件；
3. 发现函数，分配稳定 ID，提取源码和范围；
4. 发现调用，并在语言语义足够明确时解析目标；
5. 输出候选入口与语言级诊断。

它不能：

* 直接写入 `CodebaseSnapshot` 或图索引；
* 修改其他前端产物；
* 以通用字符串匹配猜测跨语言调用；
* 让语言特有对象进入公共结果模型。

VBA 前端应自行处理大小写不敏感、窗体事件、模块和类。Java 前端应自行处理包、重载和类型。核心无需也不应出现这些分支。

### 跨语言链接器

跨语言调用经常不是普通语法调用，因此链接器是独立适配层。它读取不可变的聚合分析事实，并输出“某个尚未确定调用可链接到哪个函数”的更新和证据。

可接受的证据包括 HTTP 方法与路由、IDL/RPC 服务和方法、消息主题与消费者声明、受控的人工映射。仅靠相同名称、模糊注释或目录接近性不可接受。

多个链接器若为同一调用提出不一致目标，核心不应选择“最后一个”；必须保留未解析状态并产生冲突诊断。

## 诊断与失败策略

架构要将错误分为三类，避免前端用异常控制正常分析流程：

| 类别 | 示例 | 对快照的默认影响 |
| --- | --- | --- |
| 输入/配置错误 | 重复路径、无前端、多个前端支持 | 记录错误；其他独立文件仍可形成部分结果。 |
| 语义不确定 | 未解析调用、多个候选跨语言目标 | 保留调用与证据，绝不建边。 |
| 违反核心不变量 | 重复函数 ID、调用来源不存在 | 拒绝该冲突事实，记录错误，不能产生不一致索引。 |

意外的编程错误不应被宽泛捕获后伪装成成功。扩展边界可将预期的解析失败转换为有位置的诊断；无法恢复的运行时故障应明确传播，并带上扩展身份和输入上下文。

## 可维护性机制

### 单向依赖与接口防腐层

核心不得导入 VBA/Java/PLSQL 包；公共 API 不得导入具体前端；前端不得依赖图索引实现。若外部解析器或 LSP 的数据模型复杂，应在前端内转换为 `FileAnalysis`，形成防腐层，防止第三方类型扩散。

### 小而稳定的扩展契约

前端和链接器只交换公共值对象。新增字段需有默认值或明确版本门槛；不能通过让核心认识某个前端的特殊类型来“快速修复”语义问题。

### 可替换的内部实现

函数表、正反向索引、遍历、缓存、持久化和全量/增量刷新都应隐藏在核心内部。替换时以外部可观察行为为准：函数 ID、边、排序、诊断、上下文和影响入口必须等价。

### 契约测试优先

每个前端都应运行同一组契约测试：唯一文件归属、稳定 ID、准确范围、调用来源、跨文件/前向引用、未解析诊断、确定性。核心应有独立 fixture 覆盖循环、入口管理、预算截断、刷新新增/删除，以及旧新图影响计算。链接器 fixture 需要同时覆盖可证实与同名歧义场景。

## 演进与兼容性

公共模型、诊断代码和稳定 ID 形态都属于兼容性承诺。演进遵守：

1. 新增可选字段、查询过滤器或诊断代码通常是向后兼容的。
2. 改变 ID 形态、默认查询范围、诊断严重级别或未解析调用是否成边，必须视为破坏性变更。
3. 公共 API 需要替换时，先提供旧新并存的适配层和迁移说明，再于主版本升级移除。
4. 前端/链接器契约单独版本化；核心在加载时验证兼容范围，不依赖隐式鸭子类型。

## 推荐的文档阅读顺序

1. [`design.md`](design.md)：先理解调用者为何需要这些能力，以及每条旅程的交互。
2. 本文：再理解能力如何由分层、数据流和扩展边界实现。
3. `spec.md`：在设计结论确认后，作为精确、可验收的公共契约。
4. `frontend.md` 和 `maintainer.md`：在前两份文档稳定后，分别承载插件契约与实现/测试指南。

架构是否成功的标准是：新调用者只读 `design.md` 就能完成主要任务；新前端作者只读扩展契约就不会破坏核心；核心实现者替换索引或刷新算法时，无需要求调用者修改代码。
